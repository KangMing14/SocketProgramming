## Entry 1 — Choosing a Reproducible Build System

**Problem identified:** The repository initially contained source files but no
machine-independent Visual Studio solution. A solution assembled manually on
one computer could contain machine-specific paths and could fail when cloned
by another team member or by the instructor.

**Prompt:**

> “When we submit our code, we have to ensure everything work when cloned to
> the teacher's device. Is there anything we could do, like making CMake or
> something.”

**Raw AI output excerpt:**

> “Use CMake as the source-of-truth build configuration. Define separate
> targets for the shared protocol, server core, client core, executables, and
> tests. A clean clone should be configured with `cmake -S . -B build` and
> built without relying on a local `.sln` file.”

**Critical analysis and refinement:**

The suggestion addressed reproducibility, but I did not accept the proposed
single shared library automatically. The client and server contain classes
with overlapping names and different responsibilities, so compiling both
trees into one target could cause symbol redefinition and include-path
conflicts. I refined the design into separate client and server targets, with
only genuinely shared protocol code placed in a common target. I also treated
the build as reproducible only after configuring and compiling it from the
repository rather than relying on an existing IDE configuration.

**Result:**

The project uses CMake targets for the protocol, server, client, and tests.
The build command and test command are documented in the README.

## Entry 2 — Detecting a Cross-Module Packet-Size Mismatch

**Problem identified:** Different modules used different payload sizes. One
part of the RDT implementation used `MAX_PAYLOAD = 1000`, while file I/O used
a chunk size of 1024 bytes. This could cause truncation or a buffer-size
error at the boundary between file reading and packet construction.

**Prompt:**

> “The `MAX_PAYLOAD` and `CHUNK_SIZE` values are different in different
> modules. Could this cause a problem? Please inspect the affected code and
> explain what should be changed.”

**Raw AI output excerpt:**

> “The values must have one authoritative definition. If the sender reads a
> 1024-byte chunk but the packet buffer or protocol limit is 1000 bytes, the
> implementation can truncate data or write beyond the intended buffer. Put
> the protocol limit in shared constants and make file chunking use that same
> value.”

**Critical analysis and refinement:**

I checked the claim across the sender, receiver, file handler, and packet
builder instead of changing only the first constant found. I also separated
the transport checksum from file-integrity hashing: the 16-bit packet checksum
is for detecting corruption of an individual RDT packet and is not intended
to replace SHA-256 file verification. The final change centralized the payload
limit and updated every affected call site.

**Result:**

The sender and receiver now use the same protocol payload limit. The change
was checked with the transfer tests, including normal and empty-file cases.

## Entry 3 — Fixing the RDT Header Dependency

**Problem identified:** `ProtocolConstants.h` needed the size of `RdtHeader`,
while `RdtHeader.h` needed protocol constants. Including both headers created
a circular dependency. A temporary literal header size had been introduced,
which could become stale if the structure changed.

**Prompt:**

> “There is a circular include because `RdtHeader.h` needs
> `ProtocolConstants.h` for `MAX_PAYLOAD`, while `ProtocolConstants.h` needs
> `RdtHeader.h` for `sizeof(RdtHeader)`. What is the proper solution instead
> of hardcoding the header size?”

**Raw AI output excerpt:**

> “A forward declaration cannot be used for `sizeof` an incomplete type. The
> size should be derived where the complete `RdtHeader` definition exists,
> or the dependencies should be split so that the structure does not depend
> on a header that depends on the structure.”

**Critical analysis and refinement:**

I rejected the idea of keeping a hardcoded value merely because the current
packed layout happened to be 16 bytes. I moved the derived header-size check
next to the complete structure definition and kept independent constants in
the protocol constants header. This makes a future layout change fail at
compile time rather than silently leaving an incorrect wire-format value.

**Result:**

The circular include was removed and the header layout is checked from the
actual C++ structure. The implementation and documentation now use the same
16-byte wire-format assumption.

## Entry 4 — Implementing Active-Mode `STOR`

**Problem identified:** The server supported the control command path for
some transfers, but active-mode upload (`PORT` followed by `STOR`) was not a
complete end-to-end operation. The server rejected the active upload path and
the client lacked the full data-channel orchestration.

**Prompt:**

> “Please trace the complete `PORT` + `STOR` upload path. Identify what is
> missing on the client and server, including the RDT handshake, socket
> ownership, final packet, and FTP control replies.”

**Raw AI output excerpt:**

> “Active `STOR` is not only a command-dispatch change. The client must create
> and advertise a data endpoint, the server must initiate the expected RDT
> handshake, both sides must retain the correct UDP socket for the transfer,
> and the control channel must report `150`, then `226` or an appropriate
> failure reply. The final packet must carry `FIN`; an empty file needs a
> zero-length `DATA|FIN` packet.”

**Critical analysis and refinement:**

I used the response as a checklist, then inspected the existing `RETR` and
`PASV` flows for consistency. A key refinement was preserving the same UDP
socket from the active handshake through data reception; creating a second
socket would make the advertised endpoint and the actual receiver disagree.
I also required bounded retries and peer validation rather than accepting any
incoming packet as the handshake response.

**Result:**

Active-mode upload was completed across the control and data paths. The
transfer matrix covers `PORT`/`PASV`, `STOR`/`RETR`, empty files, and a dropped
handshake packet.

## Entry 5 — Diagnosing a Silent Transfer Hang

**Problem identified:** A chaos/integrity test continued running after the
last visible ACK message and produced no further output. This indicated a
possible infinite retry or timeout loop rather than an ordinary assertion
failure.

**Prompt:**

> “The chaos test prints ACK messages for a while, then stops printing while
> the executable remains running. Please trace the sender and receiver timeout
> loops and explain why it can hang.”

**Raw AI output excerpt:**

> “A defined retry constant is not sufficient if the loop never checks it.
> The sender can retry forever after packet loss, while the receiver can also
> remain in a timeout loop without a termination condition. Add bounded retry
> handling and an explicit failure path, and log timeout decisions so the
> failure is observable.”

**Critical analysis and refinement:**

I did not treat the absence of output as proof of a network problem. I first
used the last printed sequence number and the process state to narrow the
problem to timeout/retry logic. I then checked that a retry limit would not
prematurely terminate a valid delayed packet exchange. The final refinement
was to use bounded retries with a clear transfer failure, rather than an
unbounded loop that could make the test appear frozen.

**Result:**

The chaos test has bounded failure behavior and reports a failed transfer
instead of hanging indefinitely. This was verified separately from GUI or LAN
testing; loopback success does not prove Windows Firewall or remote-network
connectivity.

## Entry 6 — Validating the Final Implementation

**Problem identified:** Compilation alone could not prove that the control
protocol, UDP transfer, empty-file behavior, retry handling, and endpoint
reuse all worked together.

**Prompt:**

> “Design a regression-test matrix for the FTP/RDT implementation. Include
> active and passive modes, upload and download, empty files, handshake loss,
> invalid `PORT` input, and transfer endpoint reuse.”

**Raw AI output excerpt:**

> “Test the Cartesian product of transfer direction and data mode, then add
> boundary cases: zero-length files, malformed addresses, a dropped SYN, a
> missing FIN, and a second transfer without stale socket state. Assert both
> the data result and the expected FTP control reply.”

**Critical analysis and refinement:**

I narrowed the matrix to cases supported by the current implementation and
kept protocol tests separate from claims about manual GUI behavior. I checked
that a passing loopback test demonstrates local correctness only; it does not
demonstrate LAN routing, firewall configuration, or behavior on the
instructor's machine.

**Result:**

The final recorded local verification covered 10 deterministic tests, with
the build, test suite, warning-enabled compilation, chaos integrity, and
whitespace checks passing at the time of verification. The verification scope
was explicitly limited to the local environment.

## Overall reflection

The most useful role of GenAI in this project was suggesting hypotheses,
pointing out interactions between modules, and proposing test cases. The
important engineering work was checking those suggestions against the actual
protocol and source code. Several suggestions required refinement: a shared
client/server library was structurally unsafe, a checksum was confused with
file hashing, and a successful local test could not be generalized to LAN
connectivity. These cases demonstrate that AI-generated output was reviewed,
adapted, and verified rather than copied without critical analysis.
